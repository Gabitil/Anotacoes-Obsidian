

 - **Processo**: Um programa que está rodando no computador (como seu navegador ou um jogo).
    
- **Espaço de endereçamento virtual**:
    
    - É como se cada programa tivesse sua **própria "cidade da memória" particular**, isolada dos outros programas.
        
    - O sistema operacional cria essa "ilusão" para evitar que um programa bagunce a memória de outro.



Antes de começarmos a construir o alocador de memória, você precisa entender como a memória de um programa é organizada. Um processo (programa em execução) opera dentro do seu próprio _espaço de endereçamento virtual_, que é separado do espaço de memória de outros processos. Esse espaço de memória virtual geralmente é dividido em 5 partes

1. **Seção de Texto**: Parte que contém as instruções binárias a serem executadas pelo processador.
	1. **O que é**: Manual de instruções do programa.

2. **Seção de Dados**: Contém dados estáticos inicializados com valores **não zero**.
	1. **O que é**: Variáveis globais/iniciais **já pré-configuradas**.
	2. **Exemplo**:

```
int salario = 5000; // Variável global inicializada
```

3. **BSS (Block Started by Symbol)**: Contém dados estáticos inicializados com **zero**. Dados estáticos não inicializados explicitamente no programa são automaticamente zerados e armazenados aqui.
	1. **O que é**: Variáveis globais **vazias ou zeradas**.
	2. **Exemplo**:

```
int contador; // Automaticamente = 0
```
3. **Heap (Monte)**: Contém os dados alocados dinamicamente.
	- **O que é**: Área de **alocação dinâmica**. Você controla quando adiciona/remove dados.
    
	- **Analogia**: Sala de armazenamento com caixas empilhadas aleatoriamente. Você decide o tamanho das caixas (malloc) e quando removê-las (free).

4. **Stack (Pilha)**: Contém variáveis automáticas (locais), argumentos de funções, cópias do ponteiro base, etc.
	- **O que é**: Gerencia funções e variáveis **temporárias**.
    
	- **Analogia**: Pilha de pratos: novos pratos vão por cima (funções ativas), e só se remove do topo (quando a função termina).

---
### **Por que isso importa para o ALOCADOR?**

- Seu alocador atuará principalmente no **Heap**: você criará funções como `meu_malloc()` e `meu_free()` para gerenciar blocos de memória nessa região.
    
- O **Stack** é automático (não precisa gerenciar manualmente).
    
- **BSS/Dados** são fixos (alocados quando o programa inicia).
---
```
|---------------|
|    Stack      |  ↓ Cresce para baixo (funções ativas)
|---------------|
|      ↓        |
|               |
|      ↑        |
|---------------|
|     Heap      |  ↑ Cresce para cima (malloc/free)
|---------------|
|     BSS       |  → Variáveis globais "zeradas"
|---------------|
|  Dados Inic.  |  → Variáveis globais inicializadas
|---------------|
|    Texto      |  → Código do programa (read-only)
|---------------|
```

As vezes as seções de Dados, BBS e Heap são chamados de **Segmento de Dados** em que, em seu fim, é demarcado por um ponteiro um ponteiro chamado "program break" ou **brk**. Ou seja, o *brk* aponta para o fim do heap.

Agora, se queremos alocar mais memoria para o heap, então vamos precisar solicitar ao sistema que incremente o brk e fazer o mesmo para liberar a memoria.

Supondo que estejamos no Linux (ou sistema Unix-like), podemos usar a chamada de sistema `sbrk()` para manipular o program break:

- `sbrk(0)` → Retorna o endereço atual do brk
    
- `sbrk(x)` (valor positivo) → **Aumenta** o brk em `x` bytes (aloca memória)
    
- `sbrk(-x)` (valor negativo) → **Diminui** o brk em `x` bytes (libera memória)
    
- Em caso de falha, retorna `(void*) -1`
    

Sendo honesto, o `sbrk()` não é a melhor opção em 2015. Existem alternativas melhores como `mmap()`. O `sbrk()` não é thread-safe e só pode crescer/diminuir em ordem LIFO (último a entrar, primeiro a sair). Se executar `man 2 sbrk` no Macbook, verá:

> _"As funções brk e sbrk são relíquias históricas dos dias anteriores ao gerenciamento de memória virtual."_

Porém, a implementação do malloc na glibc ainda usa `sbrk()` para alocações menores. Então usaremos `sbrk()` para nosso alocador simples."

### Explicação Simplificada:

1. **Crescimento oposto**:
    
    - Imagine dois irmãos (stack e heap) puxando uma corda para lados opostos
        
    - **Stack** ↓ (cresce para baixo)
        
    - **Heap** ↑ (cresce para cima)
        
2. **brk = Guardião do Heap**:
    
    - É um "ponteiro-guarda" que marca onde o heap termina
        
    - Para expandir o heap: movemos o brk para cima
        
    
    c
    

3. // Antes: [heap existente] | brk
    sbrk(100); // Aloca 100 bytes
    // Depois: [heap existente][novo espaço] | brk
    
4. **sbrk() - O "Telefone" do Sistema**:
    
    - Funciona como um walkie-talkie para negociar memória com o sistema operacional
        
    - Só pode liberar memória na ordem inversa da alocação (como desempilhar)
        
5. **Por que ainda usamos?**
    
    - É mais simples para iniciantes entenderem alocação básica
        
    - Alocadores reais usam `sbrk()` para pequenos blocos + `mmap()` para grandes blocos

### Analogia Prática:

Pense no heap como um **terreno baldio**:

- `brk` é a cerca no fim do terreno
    
- `sbrk(100)` → Mova a cerca 100m para o norte (ganha novo espaço)
    
- `sbrk(-50)` → Recue a cerca 50m para sul (devolve espaço)
    
- Você só pode devolver espaço **do fim para o começo**
    

> ⚠️ Limitação: Não pode "criar buracos" no meio do terreno! Isso exige técnicas avançadas que veremos depois.


**malloc()**  
A função `malloc(size)` aloca `size` bytes de memória e retorna um ponteiro para a memória alocada. Nosso `malloc` simples será:


```
void *malloc(size_t size) {
    void *block;
    block = sbrk(size);
    if (block == (void*) -1)
        return NULL;
    return block;
}
```


No código acima, chamamos `sbrk()` com o tamanho dado. Se tiver sucesso, `size` bytes são alocados no heap. Fácil, não?

**O problema real é o `free()`**  
A função `free(ptr)` libera o bloco de memória apontado por `ptr` (que deve ter sido alocado por `malloc()`). Mas há dois grandes problemas:

1. **Como saber o tamanho do bloco?**  
    Atualmente não armazenamos essa informação em lugar nenhum.
    
2. **Só podemos devolver memória no FINAL do heap**  
    A memória do heap é contígua como um pão francês: só podemos "cortar" pedaços do final. Não podemos devolver um bloco no meio!
